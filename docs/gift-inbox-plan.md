関連: [`codex-signed-distribution-prompt.md`](codex-signed-distribution-prompt.md)(Gift v2・署名・友達の TOFU は**実装済み**)、[`static-catalog-plan.md`](static-catalog-plan.md)(同じ Cloudflare アカウント・ドメインを使う)、[`decisions.md`](decisions.md)(「Gift は…アカウント・サーバー抜き」を本書で**拡張**する。ファイルとコードでの配布は**そのまま残す**)。

## 目的

今の Gift は「封をした `.peta` ファイルを AirDrop やメッセージで運ぶ」。これに加えて、**友達コードを交換した相手に、ファイルを運ばなくても Gift が届く**ようにする(受信箱)。

- **アカウントは作らない**。メール・電話番号・名前は取らない。**端末の鍵が住所**(公開鍵のハッシュ)。
- **サーバーは中身を読めない**(エンドツーエンド暗号化)。置き場所は Cloudflare(Workers + R2 + D1)。
- 既存の Gift のルールは**変えない**(コピー、エディション、8MB 上限、PNG 検証、署名、TOFU、`gift_already_received`、元の写真は入れない)。受信箱は**運び方が増えるだけ**で、中身は今の Gift v2 と同じ。
- **ファイル/コードでの Gift は残す**(サーバーが落ちても、オフラインでも渡せる)。

## 決めたこと

1. **住所 = 端末の署名鍵**(既存の Ed25519)。受信箱 ID は `Base32(SHA-256(署名公開鍵)の先頭16バイト)`。
2. **友達コード**を渡して友達になる(§友達と許可)。**友達の追加は、相手の承認が要る**(承認制)。**受け取りは許可制**: 受信者が承認した相手(の鍵)からしか Gift は届かない。
3. **暗号化は端末で行う**(送り手が受信者の暗号鍵で封をする)。中身は**既存の署名つき Gift v2 ファイルをそのまま包む**。受信側は復号したあと、今の `gift_receive_file` と同じ検証・受け取りを通る。
4. **短命**: 未受け取りは **7日で自動削除**、受け取り(ダウンロード+確認)後は**即削除**。
5. **確認のタイミング**: アプリ起動時 / Gifts ページを開いたとき / 窓にフォーカスが戻ったとき(60秒以上あけて)/ 手動の「Check now」/ 起動中は **15分ごと**(友達が1人以上いて、設定がオンのときだけ。UI の常時アニメーション・常時の重い処理は入れない)。**プッシュ通知は使わない**。
6. **公開までの段階**: ①開発者版(`Peta Developer`)+友達限定のベータ → ②通報・ブロック・鍵のバックアップを整える → ③公開前チェックリストを完了して一般公開。**リリースビルドでは、③が終わるまで機能フラグで無効**にしておく。
7. **お金は扱わない**(無料)。有料化・Scraps の現金販売は別途(特定商取引法・資金決済法の確認が要る)。

## 全体の構成

```
送り手の Peta                                      受信者の Peta
  Gift v2(署名つき .peta)を作る                        ▲ 検証 → 既存の受け取り
  → 受信者の暗号鍵で封をする(ciphertext)               │ 復号
  → 署名つきで POST ─────────▶ Cloudflare Worker ◀───── 署名つきで GET / DELETE
                                 │  D1: 受信箱・許可リスト・メッセージの索引
                                 └─ R2: ciphertext(7日で自動削除)
```

- ドメイン: `gift.<domain>`(Worker の独自ドメイン)。カタログの `catalog.` `packs.` と同じ Cloudflare アカウント。
- Worker のコードは `cloudflare/gift-inbox/`(TypeScript、`wrangler.toml`)に置く。**秘密鍵や公式鍵は Worker に置かない**(Worker は署名の**検証**だけ)。

## 鍵と友達コード

- **端末の鍵(既存)**: Ed25519 署名鍵(`device_key.rs`)。
- **暗号鍵(新規)**: X25519。署名鍵とは**別の鍵**として生成し、同じ場所に 0600 で保存(Keychain への移行を見越して、読み書きは1モジュールに閉じる)。署名鍵とは**署名で結びつける**(署名鍵が暗号公開鍵に署名する)。
  - 代替案(Ed25519 → X25519 の変換で鍵を1つにして、コードを短くする)は、採用するなら理由を report に書く。**目標: 友達コードは貼り付けで共有できる長さなら可、QR とリンクも用意**。
- **暗号方式**: HPKE(RFC 9180、Base モード、DHKEM(X25519, HKDF-SHA256)、HKDF-SHA256、ChaCha20-Poly1305)か、同等のよく監査された封印箱。**自作の暗号は書かない**。使う crate は監査実績のあるもの。
- **友達コード**: `PETAF1-` + Base32(Crockford、4文字ごとにハイフン、取り違えを許容して正規化。既存のコードと同じ流儀)。中身は `version · 署名公開鍵 · 暗号公開鍵 · 結びつけの署名 · 表示名(24バイトまで)`。リンク形式 `peta://friend/<base64url>` と、QR 表示も用意する。
- **指紋**: 公開鍵の SHA-256 の先頭8文字(既存の TOFU と同じ)。友達の一覧に名前と一緒に表示する。

## 友達と許可(承認制)

- **友達コードを相手に渡す**(AirDrop・メッセージなど。コードは「この人に送ってよい」と選んだ相手にだけ渡す)。
- **コードを受け取った側(Bob)が友達にしたい場合**: Bob のアプリで Alice のコードを貼る →
  1. Bob は Alice の暗号公開鍵を得るので、**友達リクエスト**(Bob の友達コード + 表示名 + 一言(最大 80 文字、任意)を、Alice の暗号鍵で封をしたもの)を Alice の受信箱の「リクエスト」へ置く。
  2. Bob は**自分の許可リストに Alice を入れる**(自分から頼んだ相手なので、Alice からの Gift は受け取ってよい)。
  3. Bob の画面は「Request sent to Nao」(承認待ち)。**承認されるまで Gift は送れない**。
- **Alice の画面**(Settings → Friends、Gifts ページの上部、サイドバーの Gifts のバッジに含める): 「Bob(指紋 ABCD-EFGH)wants to be friends」+ 一言 + **Approve / Decline / Block**。
  - **Approve**: Bob の署名鍵のハッシュを Alice の許可リストに入れる(サーバーへ署名つき `PUT`)+ Bob の友達コードを友達として保存。→ **双方向に送れる**(Bob は申請時に Alice を許可済み)。Bob には次の確認で「Nao accepted」が分かる(Bob のアプリがリクエストの状態を確認する。サーバーは許可リストの変更で判定)。
  - **Decline**: リクエストを消す。Bob には通知しない(Bob の画面は期限 7日で「No response」)。再申請は可能。
  - **Block**: リクエストを消し、その鍵からの以後の申請・Gift を拒否(サーバーの拒否リストに入れる)。
- **迷惑対策**: リクエストの宛先は受信箱ごとに**未処理 20件まで**、同じ送り手からは**未処理 3件まで**、送り手ごとに**1日10件まで**、**7日で自動削除**。Block された鍵は再申請できない。友達コードを作り直したい場合(コードが漏れたとき)は、Settings の「New friend code」(新しい受信箱に切り替える。古い友達には再度コードを渡す。**P2**)。
- **許可していない相手が Gift を送ろうとすると** `403 not_allowed`。送り手には「Nao hasn't accepted you yet.」と表示する。
- **友達から外す / ブロック** = 許可リストから外す + ローカルで拒否。受け取り済みの Gift は消さない。
- 許可リストの更新は、受信者の署名つきリクエスト(`PUT`)でだけ行える。
- 既存の `friends(public_key, name, first_seen_at)` を拡張する(**DB V9**、V8 → V9 のマイグレーションとテスト): `enc_public_key`、`status`(`requested`(自分が申請中)/ `pending`(相手の申請を承認待ち)/ `friend` / `blocked`)、`allowed`(受信許可)、`added_at`。受信箱の登録状況は `meta` に。

## API(Worker)

すべて HTTPS。リクエストは**署名つき**(`X-Peta-Key`(署名公開鍵)・`X-Peta-Time`(UNIX 秒、±5分)・`X-Peta-Nonce`(16バイト)・`X-Peta-Sig`(メソッド・パス・時刻・nonce・本文の SHA-256 への Ed25519 署名))。Worker は WebCrypto の Ed25519 で検証し、**nonce は10分間保存して再利用を拒否**する。

| メソッド・パス | 誰が | 内容 |
|---|---|---|
| `POST /v1/mailbox` | 受信者 | 受信箱を作る(署名公開鍵・暗号公開鍵・結びつけの署名)。冪等 |
| `PUT /v1/mailbox/{id}/allow` | 受信者 | 許可する送り手の鍵ハッシュを追加/削除(署名つき) |
| `POST /v1/mailbox/{id}/requests` | 申請者 | 友達リクエスト(受信者の暗号鍵で封をしたもの、最大 2KB)を置く。**許可リストに無くても可**(承認制のため)。署名つき・上限あり。拒否リストの鍵は `403` |
| `GET /v1/mailbox/{id}/requests` / `DELETE …/{rid}` | 受信者 | 未処理のリクエストの一覧/取得・削除(承認・辞退・ブロックのあと) |
| `POST /v1/mailbox/{id}/messages` | 送り手 | ciphertext を置く。ヘッダに送り手の署名公開鍵。**送り手のハッシュが許可リストに無ければ `403 not_allowed`**。`messageId`(送り手が作る128bit)で**冪等** |
| `GET /v1/mailbox/{id}/messages` | 受信者 | 未受け取りの一覧(`messageId`・サイズ・受信時刻。**送り手の鍵ハッシュは含める**。ブロック判断のため) |
| `GET /v1/mailbox/{id}/messages/{mid}` | 受信者 | ciphertext を返す |
| `DELETE /v1/mailbox/{id}/messages/{mid}` | 受信者 | 受け取り確認 → R2 と索引を**即削除** |
| `POST /v1/report` | 受信者 | **受信者が同意して**復号済みの内容と送り手の鍵ハッシュを通報として送る(運営者の確認用の保管庫。§通報) |

- 保存先: **R2** に ciphertext(**ライフサイクルルールで7日後に削除**)、**D1** に受信箱・許可リスト・メッセージ索引・nonce。
- 上限(Worker 側で強制、数値は設定にして後から調整。リクエストの上限は§友達と許可): ciphertext 1通 **8MB + 暗号のオーバーヘッド以内**、受信箱あたりの未受け取り **50通**、送り手ごとに **1日30通**(受信箱ごと・全体)、受信箱の作成は IP あたり1時間に数回。Cloudflare の**レート制限ルール**(ダッシュボード側の設定。オーナーの作業)も併用する。
- **サーバーが見えるもの(メタデータ)**: 受信箱 ID、送り手の鍵ハッシュ、サイズ、時刻、リクエスト元 IP(Cloudflare 側)。**内容は見えない**。ログは必要最小限(Worker のログに IP や鍵を出さない。保持期間を短く)。

## 送信・受信の流れ(アプリ)

**送る**(Gifts → Send → 「To a friend」/「Save a file」を選ぶ。後者は今の動作):
1. 既存の `build_gift` で Gift v2 を作る(コピー・エディション・署名)。
2. 受信者の暗号公開鍵で封をし、`POST`。**失敗したらエディション番号を消費せず、中途半端な状態を残さない**(二相: アップロード成功の確認後に確定)。`messageId` で再送しても重複しない。
3. `not_allowed` は「相手がまだ承認していません」と表示。

**受け取る**:
1. 確認のタイミング(§決めたこと 5)で `GET` の一覧 → 新着があれば `GET` で取得 → 復号 → **既存の署名検証・TOFU・サイズ/PNG 検証・`gift_already_received` を通して受信箱へ** → 成功したら `DELETE`。
2. 失敗(復号できない、署名が不正、すでに受け取り済み)の扱い: **不正なものは `DELETE` して破棄**し、ユーザーには短く表示。通信エラーは次の確認で再試行。
3. 新着はデスクトップの隅の封蝋の封筒(既存)で知らせる。メニューバーの Gift 表示・サイドバーのバッジ(既存)も更新。

**設定(Settings)に追加**: 「Check for gifts」(Automatically / Only when I open Peta、既定は友達を追加した時点で Automatically)。友達の一覧(名前・指紋・状態(Friend / Request sent / Wants to be friends)・ブロック・削除)と承認待ちのリクエスト(Approve / Decline / Block)、自分の友達コード(コピー・リンク・QR)、「Check now」。**友達が1人もいなければ、一切通信しない**。

## 鍵のバックアップと複数端末(公開前に必須)

鍵を失うと**受信箱と友達の関係が失われる**(復元手段がないため)。
- **Export identity**: 署名鍵と暗号鍵をパスフレーズで暗号化した1ファイルに書き出す(**Argon2id + ChaCha20-Poly1305**。自作しない)。**Import identity** で、再インストールや**端末の引っ越し**に復元できる。
- 鍵を失ったときの案内(「友達にもう一度コードを渡してください」)を Settings に書く。
- **複数端末で同じ鍵を同時に使うことは、公式にはサポートしない**(決定 2026-10-06)。理由:
  - Gift は受け取り確認のあとサーバーから消えるため、**先に確認した端末にだけ届く**。もう一方には届かない。
  - ステッカー帳・友達・エディションは**各端末のローカルに保存**され、同期されない。同期にはステッカー帳のサーバー保存(アカウント相当)が要るので、別フェーズ。
  - アカウントに紐づけても、同期がなければ**同じ問題**が残る。
- **Import は引っ越し用**。Import したら、古い端末では受信確認をオフにする案内を出す(強制はできない)。同時使用した場合の挙動(先に確認した端末に届く)を Settings に書く。
- 将来、ステッカー帳の同期を作るなら、**端末ごとの鍵を持つ方式**(友達は各端末に1通ずつ送る)か、**アカウント**が要る。そのときに再検討する。

## 通報・ブロック(公開前に必須)

- **運営者は内容を見ない**(通信の秘密)。見るのは、**受信者が同意して通報したとき**だけ。
- 受信した Gift の詳細に「Report…」(理由の選択 + 同意の確認)。同意すると、復号済みの Gift と送り手の鍵ハッシュを `POST /v1/report` で送る。**運営者は通報の保管庫でだけ確認する**(R2 の非公開バケット。保持は対応後30日まで)。
- 対応: 該当する送り手の鍵を **Worker の拒否リスト**に入れる(以後、全受信箱への送信が `403`)。違法な画像の疑いがあるものは、**削除より先に保全の要否を弁護士に確認**する。
- ブロック(受信者個人の拒否)は、通報とは独立にいつでもできる。
- **通報の確認は、オーナー(あなた)が行う**(決定 2026-10-06)。**目安は3日以内**に確認し、該当する送り手の鍵を拒否リストに入れる(ベストエフォート。友達限定ベータの間はこれで足りる)。
- 通報が届いたことに気づけるよう、Worker から**オーナー宛に通知**する(メール、または Discord などの Webhook。どれにするかはオーナーが決める)。通知に**画像や内容は入れない**(通報の件数と ID だけ)。
- 連絡先(メール)を利用規約・アプリ内・App Store のページに載せる。

## 守ること・できないこと

- **「1つの Gift は1回だけ受け取れる」**は、サーバー経由の受信箱では**全端末で**保証される(ファイル/コードの Gift は従来どおり端末ごと)。
- **プッシュ通知はできない**(確認のタイミングでしか届かない)。
- **送った後の取り消し**は、受信者が受け取る前なら可能(送り手の署名つき `DELETE`)。受け取り後は不可。
- **運営者が内容を検査して不適切なものを防ぐことはできない**(設計上、見えない)。対策は許可制・ブロック・制限・通報。
- **メタデータ(誰が誰に、いつ、どれだけ)はサーバーに残る**(7日以内に消える)。プライバシーポリシーに書く。
- **鍵の紛失は復元できない**(Export の備えが前提)。
- **端末の時計が大きくずれていると**署名つきリクエストが拒否される(±5分)。

## コスト(見積もり。正確な料金は公式で確認)

- R2・D1 は、通常の使い方で無料枠に収まる見込み(ciphertext は削除されるので保存は常に小さい)。
- **Workers の無料枠は1日10万リクエスト**。15分ごとの確認は、**1人あたり1日最大96リクエスト**なので、**アクティブなユーザーが約1,000人を超えると無料枠を超える**。そのときは有料プラン(月5ドルで月1,000万リクエスト、超過は100万あたり0.30ドル)にする。確認間隔は設定値にし、新着がない間は間隔を延ばす(バックオフ)。
- ドメインは既存のもの。
