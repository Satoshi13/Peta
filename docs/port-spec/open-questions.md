## 追加提案P2: 素材の分解とMarket交換（2026-10-04）

オーナーから「素材分解からのスクラップでの引換機能を先に完成させたい」「MarketとMaterialsの右上にスクラップ数」と依頼があった。以下の既存推奨案・比率を初期仕様として実装する。比率の個別指定はなかったため、提案値を採用する判断を作業時に明示した。RustのルールとUIは別コミット。O3の現金購入・未実装素材の付与は引き続き未提供。

### 採用する初期仕様

- 共通の交換アイテムを1種類にし、英語名は`Scraps`。素材別の欠片にすると複数の残高・必要な組み合わせが増えるので、最初は不要な素材を好きな商品へ交換する単純な流れを推奨する。
- 分解は未使用のKraft／Holographicの在庫だけ。無制限のMatte・作成済みステッカー・Giftは対象外。素材帳の発見履歴は残す。
- Materialsはカードクリックでプレビューだけを開き、Create用素材を選ばない。カードの下とプレビューに`Dismantle…`を置く。数量と`Receive N Scraps`、確定後の素材残数を示し、確認してから消費する。Createの素材ピッカーには分解ボタンを混ぜない。
- MarketとMaterialsの見出し右上に残高を小さく示す。素材／Packの詳細に交換価格と`Exchange`を置き、確認欄で商品・数量・消費Scraps・残高を示す。不足なら交換不可、キャンセルや閲覧では消費しない。
- 交換できる素材は実装済みKraft／Holographic。Gold／Riso／Vintageの実装・新素材画像、O2の決済・O4の作者機能は含めない。
- Packは実装済みの無料Tokyo／Coffee／Houseplantsから始め、初回の無料取得は維持する。**空になった同じ袋を補充する**。既存の袋へ同じセットを追加し、開封済み項目・履歴を残す。袋の総数は累計、残数は未開封数となるのでUIにも明示する。まだ中身がある袋の追加補充は最初は不可。別案は「別の袋を毎回追加」だが、商品と袋の識別を分ける追加設計が必要。
- 有料表示のPixel／Cats／Nightを交換商品にするかは別途決める。現時点では未提供を維持し、金額を勝手にScrapsへ置き換えない。

### 初期の比率（実装値）

| 操作 | 素材・商品1単位あたり | 理由 |
| --- | --- | --- |
| Kraftを分解 | +1 Scrap | 基準の有限素材 |
| Holographicを分解 | +3 Scraps | 出にくい素材の交換価値を高くする |
| Kraftへ交換 | −2 Scraps、在庫+1 | 買って分解する循環で残高が増えない |
| Holographicへ交換 | −6 Scraps、在庫+1 | 同上、Kraftを集めてホロへ交換できる |
| Tokyoの補充 | −16 Scraps、8枚追加 | Packは1枚あたり2 Scrapsを基準 |
| Coffeeの補充 | −12 Scraps、6枚追加 | 同上 |
| Houseplantsの補充 | −10 Scraps、5枚追加 | 同上 |

### 保存・失敗時の扱い

現行DB v7には`meta(key,value)`、`material_stock`、`packs`、`pack_items`がある。共通Scrapsだけのローカル交換なら、`meta`へ専用キーの残高とリクエストIDごとの取引結果を保存し、**スキーマ・user_versionを変更せず実装可能**。localStorageに残高を保存せず、Rustで在庫・残高・商品付与・取引結果を1つのSQLiteトランザクションとして更新する。同じIDの再送には保存済み結果を返し、二重消費／二重付与を防ぐ。交換比率はRustの1か所で決め、JSから価格や受取数を指定できないようにする。専用の取引テーブルや同期アカウントが必要になった場合は、既存の「DB・スキーマは変えない」に従って移行前に報告する。

受け入れ検証は、在庫不足・残高不足・Matte拒否・不正数量・未提供商品・重複送信・途中失敗でのロールバック・再起動後の残高／取得品・発見履歴保持・既存のWelcome／Market／Gift／FIFOの回数と順序。追加の常時ポーリングやアニメーションは使わない。

**適用範囲:** 共通Scraps＋上表＋無料3Packの空袋補充。残高の初期値は0。数量は1〜1000枚、Pack補充は1袋ずつ。O1〜O5の他の未決事項は変更しない。新素材・有料Pack・同期・専用取引テーブルへ広げる際は別途設計する。
