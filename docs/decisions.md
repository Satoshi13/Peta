## 用語メモ: 「MVP」とは

Minimum Viable Product。**「最初に世に出して検証する、最小の版」**のこと。
Gift / Pack を「作らない」のではなく、**「最初のAlphaには入れず、あとで順に入れる」**という順番の話。

Gift はアカウント・サーバー・送受信が必要で、実装が一気に重くなる。一方、Peta の核
(「毎日1枚作って貼り、翌日もそこにある」が楽しいか)は Gift なしで検証できる。
そこで次の順にしている(仕様 §71-79):

1. Phase 0-5: デスクトップ / 1日1枚 / 作る / コレクション ← **ここまでが MVP(最初のAlpha)**
2. **Phase 6: Pack**(ローカルのみ。サーバー不要なので早めに入れられる)
3. **Phase 7: Account + Gift**
4. Phase 8: Marketplace

# 2026-10-11 実装追記：本物・複製・Gift v3

V12 で本物は held/gone の記録として保持し、譲渡の来歴を残す。移動するとその複製・配置・印刷待ち・タグを一つの SQLite トランザクションで整理する。Gift 保存は隣接一時ファイルと復旧ジャーナルを使い、失敗時に旧ファイルを復元、次回起動時に DB の確定記録と照合する。

旧 Gift・既存データには作者の署名を捏造しない。転送するときは未検証の作者情報と現持ち主の署名つきの引継ぎ証明を使い、以後の移動だけ検証する。Gift v3 に新しい Gift の番号は付けない。原本を編集すると完成画像の作成証明を更新し、飾りの複製の画像参照も更新する。

画像の指紋は未加工の入力ファイルの完全一致だけを判定する。Scraps のボーナス支払い・類似画像検出・サーバーによる二重受領の防止は含めない。

# 2026-10-11 実装追記：Pack の版と景品

Studio の Edit chances は版の Editions に置き換え済み。新規 PETAPACK v2 は各デザインの枚数と景品・各版の作成証明/番号/release を署名に含める。DB V13 の1行は1スロットで、デザインの画像を共有する。ヘッダは版ごとの署名を運べるよう最大1MiB、ファイル全体は既存の24MiB上限。旧形式の上限と署名は変えない。

自作の原本は原版として残り pressed、一度だけ発行可能。飾り用の複製と装着済みのタグも原本に残る。受け取った本物は1枚だけ移動し、複製・配置・装着済みタグを整理。景品のタグには未装着の在庫だけを使う。素材は開発者版でも実在庫から移す。

同タイトルの再発行と補充は拒否。My shelf の自作パックは見本/在庫だけで、署名鍵を照合して開封を拒否する（旧自作パックも含む）。新形式の無料開封も残りを消費し、旧形式の無料コピーとは区別する。版の作者証明は Gift v3 で転送しても番号と総数を保持する。

審判の claim_slot はパックの公開IDとヘッダから決まるスロット番号を受け取る。SQLite の端末ごとの行番号は使わない。署名検証済みとサーバーによる番号確認は別の情報で、現時点では後者は未確認。経済の支払い・売り手の取り分はこの工程に含めない。

## 2026-10-11: Duplicate 廃止

Collection の新規複製機能は UI・IPC・権限・core の公開 API から削除。Pack の版の発行は維持し、Studio の表示は Editions とする。既存の複製は削除・本物への変換をせず、そのまま貼付・剥離・タグ・削除を利用できる。DB V13 と既存の署名形式は変更しない。同じ写真から作り直すことと旧形式の無料開封は今回の変更対象ではない。
